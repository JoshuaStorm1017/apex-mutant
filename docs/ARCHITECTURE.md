# Architecture and acceptance contract

Node/TypeScript CLI, with the BSD-licensed apex-dev-tools ANTLR parser. Modules: mutation engine (src/mutations.ts), project discovery/copy/integrity (src/project.ts), Salesforce subprocess adapter (src/salesforce.ts), org classification gate (src/orgSafety.ts), sequential runner (src/runner.ts), JSON/HTML reporters (src/report.ts), findings derivation (src/findings.ts), enforcement policy and readiness criteria (src/policy.ts), portable exports (src/exports.ts), CLI (src/cli.ts). Shared public contracts live in src/types.ts; the tool name and version exported into artifacts live in src/version.ts.

The engine exports `generateMutations(source, file): Mutation[]` and `applyMutation(source, mutation): string`. Offsets are zero-based JavaScript string offsets, end-exclusive; line and column are one-based. IDs are content-derived and deterministic.

The Salesforce adapter exports `validateWithSalesforce(options): Promise<ExecutionResult>`. It runs `sf project deploy start --dry-run --test-level RunSpecifiedTests --tests ... --target-org ... --source-dir ... --wait ... --json`. It must fail closed on missing/malformed JSON or zero executed tests. A test failure is killed only when test result evidence exists and compilation passed. Compile failures are invalid; operational failures are error. Timeouts are never killed. No raw CLI output or org identifiers are persisted in reports.

Project handling reads SFDX packageDirectories, refuses symlinks/path escapes, copies only package source plus the project configuration into a private temporary directory, and excludes auth/cache files. Each mutation starts from the same pristine snapshot. The runner validates a baseline before running mutants, writes incremental results, and cleans up on ordinary failures. There are no direct credentials or Salesforce API clients.

Score = killed / (killed + survived). Invalid/timeouts/errors are excluded and reported visibly; incomplete execution must fail CI independently of score. No valid mutants means score unavailable, never 100 percent. Resume/caching and coverage-based selection are later work; correctness comes first.

Reporting is advisory by default: `reportExitCode` reads the policy recorded in the report and may only return 1 when the caller opted into `mode: 'enforce'` with an explicit threshold. Exit code 2 ("no readable result") is independent of mode and of score. `buildFindings(report)` derives located, prioritized findings with a suggested action per operator class, keeps mutants with no test evidence in a separate lower-priority category, and reports run-level problems (failed baseline, short run) as run-quality findings rather than letting them degrade the score silently; `fileHotspots(report)` ranks files by surviving mutants. Findings are always derived from the report, never stored in it, so a partially written report can never carry stale ones.

Reports record safeguard evidence, not restatements of documented guarantees: which validator ran, whether it was the built-in validation-only path (a caller-supplied Validator is recorded as un-attested — the runner never assumes it), the org classification enforced before anything was sent, snapshot isolation, and a post-run byte-for-byte re-read of every project file (`verifySourceIntegrity`). An unverifiable check reports `verified: false` and never `unchanged: true`.

Exports (`csv`, `sarif`, `md`) are derived from the same report and written with the same atomic symlink-safe write. CSV defuses spreadsheet formula injection; SARIF never emits `error` level, and only `note` in advisory mode. Caller-supplied work-item identifiers are validated against a conservative pattern before a run starts, never sanitized after the fact. Report `schemaVersion` is 2.

Acceptance: advisory-first exit codes with both halves of any gate explicit; findings that name a location and a next action; safeguard evidence recorded per run; portable exports carrying caller-supplied traceability; deterministic syntax-aware edits; preserved original workspace; strict baseline gate; exact dry-run subprocess contract; distinct classification for test/compile/auth/timeout outcomes; offline end-to-end tests; useful JSON and HTML reports; clean npm package; public CI and handoff. Live-org validation remains a separate gate until a disposable org is provided.
